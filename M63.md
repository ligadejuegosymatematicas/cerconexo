## Infraestructura seleccionada para el piloto

Se propone **un Worker experimental con Static Assets y Durable Objects SQLite**, en su propio subdominio `workers.dev`. El mismo origen sirve portada, juego, API HTTPS y WebSockets WSS. Evita configurar dos alojamientos y CORS entre ellos durante el piloto. GitHub Pages estable permanece sin cambios. El código puede conservarse en la rama M6 de GitHub; no se requiere conectar la publicación estable ni crear una PR hacia `main`.

El servidor reutiliza el motor oficial y el adaptador autoritativo de M6.2. Se mantienen el estado por sala, las transacciones SQLite anteriores a la confirmación, revisiones, recibos idempotentes, ocho minutos compartidos por equipo y gracia limitada. Las sesiones sobreviven a recarga o reconexión y no se almacenan en los guardados locales.

`wrangler.experimental.jsonc` es local por defecto y no publica. El script `deploy-experimental.mjs` genera una configuración de publicación ignorada por Git, con nombre fijo `cerconexo-m6-experimental`, cuenta explícita y origen HTTPS exacto. Sin `--publish` ejecuta solamente una compilación en seco. Publicar exige además confirmar que la cuenta tiene Workers Free; el script no cambia planes, facturación, dominios ni permisos de GitHub.

Una vez desplegado y comprobado, el servidor se ejecutará en Cloudflare sin depender de este PC. Esa independencia **aún no se ha comprobado en producción** porque falta la cuenta. El plan gratuito no garantiza disponibilidad continua: superar cuotas o sufrir una incidencia del proveedor puede interrumpir partidas.

## Seguridad y límites del piloto

- API pública habilitada solo para su origen HTTPS configurado; WebSocket exige el `Origin` admitido. El laboratorio anterior mantiene su restricción a loopback.
- El servidor público acepta crear únicamente Clásico por ficha. Las tres modalidades siguen previstas en el modelo de infraestructura, pero las sondas de Arena no se publicitan como juego.
- Credenciales de participante de 256 bits, hashes en servidor y autenticación WebSocket en el primer mensaje. Ni invitaciones ni URL contienen secretos; no se añaden credenciales a fuentes o recursos estáticos.
- Cuerpos HTTP limitados a 8 KiB mientras se leen, incluso sin `Content-Length`; tipos y comandos mantienen su validación. Acciones duplicadas devuelven su recibo sin repetirse.
- CSP de scripts propios y hashes de los pequeños scripts inline oficiales; sin `unsafe-inline` para JavaScript. WSS del sitio explícito, `no-store`, `no-referrer`, `nosniff`, prohibición de incrustación y exclusión de buscadores. Los estilos SVG oficiales requieren estilos inline.
- Máximo inicial de **20 creaciones de sala por día globales**; se conservan límites por IP, conexión y sala de M6.1. Es un límite conservador del piloto, no una garantía de consumo total de cuenta.
- Las pantallas de resultado dejan de programar alarmas periódicas de presencia; mantienen vencimientos de autenticación y retención. Esto evita escrituras constantes al dejar abierto un resultado. La presencia se concilia cuando vuelve a haber actividad o se cierra una conexión.
- Se incorpora el aviso discreto tras 60 segundos sin acción efectiva, sin añadir un límite por turno. El reloj oficial sigue siendo el del servidor.

El permiso de escritura de scripts de Workers permite gestionar scripts, Durable Objects y el subdominio; se explicará antes de concederlo. Se preferirán los permisos `account:read`, `user:read` y `workers_scripts:write` y almacenamiento de OAuth en el llavero del sistema. Los secretos no se pegarán en el chat ni en archivos del repositorio.

Con la cuenta verificada se obtendrán su identificador y subdominio, se confirmará el plan gratuito y se preparará el origen definitivo. El script exige ese origen exacto y rechaza nombres distintos del Worker experimental. No se utilizarán cuentas temporales anónimas, túneles al PC ni servicios con vencimiento como sustituto de un servidor persistente.
